## Platform Evidence and Delivery Boundaries

Checked Expo `~57.0.32` in `package.json`, the matching [SDK 57 notification](https://docs.expo.dev/versions/v57.0.0/sdk/notifications/) and [audio](https://docs.expo.dev/versions/v57.0.0/sdk/audio/) documentation, the [Expo documentation index](https://docs.expo.dev/llms.txt) and [local Expo module workflow](https://docs.expo.dev/modules/get-started/). A native module/config change requires a rebuilt development/preview binary. Enabling background audio alone does not establish future deadline activation after JS suspension; this design uses a native scheduled alarm.

Android documents [exact alarm scheduling](https://developer.android.com/develop/background-work/services/alarms), including user-visible `setAlarmClock`, and an [exact-alarm exemption from background service launch restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start). A bounded playback service must declare the [mediaPlayback foreground service type and permissions](https://developer.android.com/develop/background-work/services/fgs/service-types#media) and [promote itself with a notification](https://developer.android.com/develop/background-work/services/fgs/launch). On Android 15+, [audio focus requires a top app or foreground service](https://developer.android.com/media/optimize/audio-focus). These sources justify the proposed Android design; they are not evidence that the new module already works on a device.

Ordinary iOS custom notification sounds must be [shorter than 30 seconds](https://developer.apple.com/documentation/usernotifications/unnotificationsound). Keep the valid existing 15-second resources; do not embed a 60-second iOS notification file. [AlarmKit on iOS 26+](https://developer.apple.com/videos/play/wwdc2025/230/) provides system alarms with explicit per-app authorization and changes silent/Focus behavior. The documented [AlarmConfiguration](https://developer.apple.com/documentation/alarmkit/alarmmanager/alarmconfiguration) reviewed here does not establish an exact 60-second automatic ringing cutoff while suspended. AlarmKit integration and altered iOS alarm semantics are not silently added to this Android-focused delivery. If full-minute iOS background parity becomes a user requirement, retain it as unmet until a supported design and physical evidence are established.

Respect the existing [NotificationChannel user-control contract](https://developer.android.com/reference/android/app/NotificationChannel): retain `crono.alerts.<sound>.v1` and existing resource basenames, do not delete/recreate channels to override settings. For Android service-controlled playback post a silent notification envelope on the relevant existing channel and play only through the broker, after checking effective channel/system settings; ordinary Expo fallback retains its one-shot sound. Never play both.

Delivery is conditional on notification authorization, exact-alarm special access, channel/user sound settings, OEM restrictions and the device being powered on. User force-stop, reboot restoration, app uninstall and guarantees through system audio interruptions are outside this request. No boot-time playback service, full-screen intent, overlay, critical-alert entitlement, battery exemption request, repeated-notification workaround or audio loop to keep JS alive. Ordinary process reclamation of an armed Android app remains in scope.

## Proposed Ownership and Interfaces

1. Keep `notificationCoordinator` as the sole JS OS reconciliation owner. Add a composed Android adapter: when the new module and exact capability are usable, its future delivery uses the native backend; otherwise preserve ordinary SDK notification delivery with explicit degraded status. Inventory/cancellation cover both backends. A semantic event must never be armed through both. If old-backend cancellation fails, block replacement for that owner and expose retry.
2. Add a separate tracked local module `modules/crono-completion-alerts/`; keep `crono-background-access` as the read-only capability probe. The new module owns an atomic native registration ledger, the next Android alarm, a single native audio broker and a bounded playback service. Pure timing calculations and editable app persistence remain in their existing layers.
3. Native delivery records contain physical registration ID, validated event payload/key (`eventId@dueAt`), content fingerprint, backend version, monotonic native generation, selected duration/sound/channel, localized content/Open/Stop labels and only the metadata needed to deliver. Persist future records before arming. Bound future records to current projection (at most one timer plus 50 schedule events), delivered receipts to 256 and buffered response to the latest validated response. Use app-private atomic storage, not AsyncStorage from a receiver.
4. Use one native scheduler for the earliest future timestamp via `AlarmManager.setAlarmClock` and an immutable explicit PendingIntent. The Android alarm indicator is an intentional visible consequence. On delivery process due records in one serialized batch, select the latest crossed boundary with R4 tie priority, mark stale/interrupted records consumed, and arm the next stored deadline independently of sound. A receiver must revalidate current record/generation/capability; no JS engine is needed. Do not switch to idle-throttled repeated alarms to simulate the sequence.
5. The native broker owns **all Android playback, including foreground alerts and previews**, so receiver callbacks cannot overlap an Expo player. iOS/web retain `createAlertPlayback`. Preserve a common controller facade (`request`, `stop`, `cancelOwner`, `getState`, `activate`, `dispose`) and add explicit lifecycle suspension/detachment rather than using user Stop for backgrounding. Extend request identity with run ID and deadline as needed. Native `request` and receiver activation atomically deduplicate the same semantic key; once delivered/consumed it cannot restart because the UI completed later.
6. Broker foreground playback can run while the activity is resumed and unlocked without a background service. A background deadline starts/promotes `CompletionAlertService` **before** requesting audio focus/playback; moving a playing completion into background transfers the same player and expiry to the service if OS opt-in/capabilities allow. A foreground-only sound or preview stops on leaving. Native activity/keyguard checks handle JS-suspended transitions. Returning merely subscribes/reads the snapshot; it does not claim a new minute or stop the service.
7. Loop the existing bundled native motif/resource URI for the selected 5/15/30/60 budget. Background delivery preserves effective Android channel sound overrides; unavailable sources fail visibly on return. Direct foreground requests/previews use the app-selected resource and native silent/audio policy independently of OS notification/exact permissions, preserving existing behavior. Recheck background capability before promoting an already playing foreground sound; stop instead of bypassing a blocked/silent channel. Start the monotonic end budget after real playback starts, use a separate four-second preparation timeout and a bounded partial CPU wake lock only for preparation/playback (maximum 65 seconds for a 60-second event). No waiting-countdown wake lock. On expiry, Stop, replacement, audio-focus loss or failure release player, focus, timers, wake lock and service. Stop on audio interruptions without replaying later. Do not force volume or bypass silent/DND.
8. The notification's Stop action carries registration/event/generation identity and reaches a non-exported receiver directly. Open uses an immutable validated app intent and the existing buffered Router flow. On natural audio end remove the service's ongoing state while retaining a normal completion notification; Stop similarly leaves a silent completed notice without an active Stop action. Notification dismissal may stop only its matching active alert. No action mutates domain timer/schedule state.
9. React owners observe accepted updates and issue explicit native cancellation/settings policy updates. Distinguish background suspension/unmount detachment from user pause/reset/replacement/mute. Stale accepted async registrations cannot revive a canceled run. Disabling OS delivery cancels its future events and stops its background audio; mute or effective sound/duration changes stop current playback and update future descriptors. Language changes update future content without restarting current audio. Failed hydration must not sync default state into native storage.

The common native interface should provide capability/version, `upsertRegistration`, `cancelRegistration`, pending/presented inventory, validated last-response/clear, `requestPlayback`, scoped `stopPlayback`, accepted-policy/run invalidation, a current playback snapshot and receipt/event subscription. Keep Android implementation behind `completionAlerts.ts` / `.web.ts` wrappers with optional-module detection; missing/old binaries cannot crash imports or claim enhanced readiness. A bridge failure after possible native acceptance must not start JS audio as a speculative retry.
