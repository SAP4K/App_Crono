# Stop preset motion before an explicit wheel choice

**Date:** 2026-11-10 21:40 (Europe/Bucharest)
**Files:** `src/hooks/useDurationWheel.ts`, `tests/e2e/timerPresetMotion.spec.ts`
**Severity:** medium

## Problem

During a Timer preset glide, immediately pressing ArrowUp accepted the correct two-minute duration but could leave the selected row 2–4 pixels away from the selection center indefinitely. Verification passed 63/64 focused browser cases; two of three subsequent diagnostic repetitions failed. The earlier 455-case pass did not establish that the intermittent cancellation path was correct.

## Root Cause

The shared `choose` method used the same presentation `interrupt()` operation as a physical drag or wheel gesture. That operation preserves the currently displayed offset and intentionally uses ordinary alignment, so a real gesture can continue from that position.

An explicit key, row or accessibility choice replaces the accepted value instead. The manual controller is idle during presentation, so its `choose` operation also used ordinary alignment. Neither step exercised the web adapter's existing compositor-cancellation frame. An obsolete smooth-scroll frame could therefore move the column slightly after the explicit choice, while no remaining selection callback would restore its center.

## Solution

Use the existing presentation `settle()` operation before delegating an explicit choice to the manual controller. It invalidates callbacks and stops the driver before using cancellation-capable alignment. The subsequent choice updates the same pending alignment to the exact selected row. Both operations happen synchronously before painting; selection and Start are not delayed.

Keep `interrupt()` for physical drag/wheel takeover, preserving its displayed-offset ownership and existing busy/inertia guards. No new state owner, timer, dependency, permission, saved setting or native configuration is introduced.

Retain the original failing browser regression unchanged and add two discoverable Home/End cases. They assert exact centering, zero-draft Start gating, valid saved duration, and absence of stale writes after the presentation fallback deadline.

## Prevention

- Separate physical continuation at the displayed offset from an explicit choice derived from the accepted value. They require different visual cancellation behavior.
- Reuse compositor cancellation for an explicit programmatic-to-key/row/accessibility handoff; assigning `scrollTop` alone is not the existing adapter's hard-stop operation.
- Keep real-frame integration checks with strict centering and persistence assertions. A passing full run does not dismiss a later reproduced intermittent failure.
- Preserve the original failing case and repeat it unchanged across a fresh export. Do not weaken pixel tolerances, increase timeouts or rerun against a cached old bundle.
- Additional coverage when physical testing resumes: interrupt native preset motion with TalkBack/VoiceOver increment/decrement, neighboring-row taps and rapid mixed touch/key input. Browser keyboard and endpoint tests do not establish native accessibility behavior.
