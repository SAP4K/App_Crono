# Reject stale native drag-release events before changing manual state

**Date:** 2026-11-13 13:09 UTC
**Files:** `src/hooks/wheelSettlement.ts`, `src/components/DurationWheel.tsx`, `tests/nativeWheelSettlement.test.ts`
**Severity:** medium

## Problem

Verification finding `verify-native-release-ownership` reproduced false native terminal proof: begin a new drag at timestamp 100, deliver an old release at 50 (or a missing timestamp), then deliver a terminal at 120. The helper accepted that terminal. In the composed native/manual-controller probe it selected value 7 and changed busy from true to false while the current drag was still held.

This was a deterministic event-order reproduction, not a physical-phone latency measurement.

## Root Cause

The helper marked a gesture released before validating the release timestamp. Its terminal check only compared the terminal with the maximum observed native timestamp, which could not establish that the preceding release belonged to the current gesture.

The native adapter also forwarded every scroll-end-drag release to the manual controller. Hardening terminal proof alone would therefore leave the controller's 160 ms fallback armed after an invalid release. A held gesture could still settle when that fallback ran.

Comparing a release with the moving scroll watermark would introduce a different rejection: a valid release can be delivered after an observation carrying a later timestamp. Gesture start and latest observation serve different validation purposes.

## Solution

- Store the current gesture's start timestamp separately from its maximum observed timestamp.
- Return false for missing/nonfinite release timestamps, missing gesture-start proof, and releases older than the current gesture start, without mutating release proof.
- Return true for a current valid release; only then may the native adapter forward the release to the manual controller.
- Keep terminal validation against the maximum observed/release timestamp. Equal timestamps remain valid.
- Preserve inertia, row alignment, accepted-value/busy ownership, presets, persistence and lifecycle cleanup. The existing 1000 ms missing-terminal watchdog still applies after a valid release.

Invalid metadata is not evidence that a held gesture ended. If a runtime omits native release timestamps and also intercepts the touch-end stream, a later valid release or lifecycle cancellation is needed; this fix does not invent a safe terminal. Installed SDK 57 / RN 0.86.3 Android and Fabric iOS payloads supply native monotonic timestamps. Physical gesture acceptance remains pending.

No routine runtime logging was introduced, retaining the user's warnings/errors-only policy. Regression assertions carry bounded `[FIX:native-release]` diagnostics with synthetic event inputs and selection/busy traces.

## Prevention

- Validate ownership at every state-changing boundary, including release; validating only final completion cannot undo an already armed fallback.
- Keep gesture-origin time separate from the moving observation watermark. Include equal-tick and delayed-valid-event positive controls so stricter filtering cannot silently reject legitimate gestures.
- Test the actual helper and composed adapter/controller protocol. Advance beyond both fallback deadlines and invoke a captured canceled callback while asserting selection remains unchanged and busy stays true.
- Inspect the production forwarding condition independently. The physical touch-end/cancel handlers are separate from scroll-end-drag; this regression does not claim arbitrary stale touch events are generation-fenced.
- Keep missing-terminal recovery after a valid release distinct from rejecting an unverified release.
- Additional acceptance: on an updated Redmi build, repeat prolonged holds, interrupted flicks and native accessibility adjustments, then measure final-stop-to-accept latency. Browser emulation and exports do not establish those results.
