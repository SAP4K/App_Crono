# Keep Settings updates outside unchanged navigator work

**Date:** 2026-11-13 16:31 UTC
**Files:** `src/app/_layout.tsx`, `tests/e2e/performance.spec.ts`
**Severity:** medium

## Problem

The performance verification left Task 9 incomplete: broader native response-time and large-data acceptance was unavailable, and the limited Redmi comparison did not demonstrate improved ordinary navigation. The user invoked `$aif-fix` immediately after the specific finding; the verification finding supplies the fix scope. No separate fix plan or renewed mode question was needed.

Investigation found avoidable navigator work during ordinary Settings opening/closing. This is a concrete source defect; it is not proof that all measured Settings mounting/window cost has the same cause.

## Root Cause

`AppShell` owns Settings visibility alongside the tab navigator. Its local update recreated Tabs options, screen elements and tab-bar callbacks. The installed Expo Router bottom-tab implementation depends on recreated descriptors and processes every route through its animation effect even when the selected route has not changed. Event emission is conditional on a route change; the animation setup itself is not.

Existing DOM-mutation/encoding tests could miss this work because rebuilding an unchanged React/navigation subtree need not change visible text. A blanket claim that React Compiler removed this cost was unsupported by the emitted bundle and actual reproduction.

## Solution

Extract a small memoized `RouteTabs` boundary. Its inputs are the actual background color, stable language catalog, route animation eligibility, measured scene width and stable height callback. Real theme/language, resize, reduced-motion and foreground changes remain inputs. Navigator internal state and descendant context subscriptions still update normally; TabBar receives current state/navigation. No second navigator/store, altered transition duration or native modal rewrite was introduced.

The registered browser regression counts actual processing of the four tab-route records in a disposable context. Opening/closing Settings and navigating its sections must do zero unchanged route-array passes; a real tab change is a positive control. Before the source change the exact check failed with four passes on Settings opening. Afterward the same check passes with zero. This proves removal of redundant route work, not direct input latency.

The user's WARN/ERROR-only logging preference overrides the generic verbose fix-logging examples. Existing bounded motion/navigation warnings remain. Test names, work counts and failure assertions provide feedback without shipped input/frame logs, new debug flags or personal payloads.

## Prevention

- Check the installed navigator's actual effect dependencies. An unchanged selected route does not guarantee that descriptors or animation setup remain idle.
- Isolate navigator construction from sheet/toast/status updates with only its real inputs. Do not freeze live route state, descendants or appearance/motion/geometry changes.
- Measure work that DOM-mutation counters cannot see; keep a meaningful real-navigation positive control.
- Preserve pre-fix failures and bind final source, runner, export and APK identities separately. Do not treat list-only discovery output, a detached wrapper or earlier-source passing cases as current execution evidence.
- Use repeated, thermally comparable native measurements before claiming improved response. Additional useful coverage is the pending physical 50-step draft/large-lap and input-to-visible journey; synthetic phone data requires the plan's explicit readiness answer.
