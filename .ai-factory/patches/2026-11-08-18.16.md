# Revalidate permission gestures at the native prompt boundary

**Date:** 2026-11-08 18:16 UTC
**Files:** `src/hooks/notificationCoordinator.ts`, `src/hooks/systemNotifications.ts`, `src/hooks/notificationTypes.ts`, `tests/notificationRuntime.test.ts`, `tests/notifications.test.ts`
**Severity:** medium

## Problem

Verification reproduced a native permission API call after the user went Home, disabled system notifications, or disposed the notification owner while channel preparation was pending. A failed hydration outcome during preparation also left the obsolete request able to prompt. The existing Home regression held the coordinator's first permission read, not the subsequent asynchronous work inside the real adapter.

These reproductions establish an invalid API invocation, not a claim that a physical OS dialog appeared. The fix request follows the reported verification finding; no separate fix plan or scope decision was needed.

## Root Cause

The coordinator checked foreground activity and saved opt-in before calling the adapter. The adapter then awaited channel preparation, module access and another permission read without rechecking whether the originating gesture was still valid. The coordinator's later response guard could suppress stale state publication but could not prevent the earlier native side effect.

Simply returning a denied capability for a skipped prompt would also mark cancellation as a refusal, suppressing a later valid implicit request in that owner lifetime.

## Solution

Pass a fresh `canPrompt` callback through the adapter contract. The coordinator derives it from current owner generation/disposal, successful hydration, saved opt-in and foreground activity. The real adapter checks current app activity and that callback before preparation and immediately before `requestPermissionsAsync`, after all asynchronous reads. There is no await between the final check and the native request.

Return `null` when preparation is cancelled. The coordinator does not record a refusal or publish the cancelled response. A genuine refusal still suppresses repeated implicit prompts, and explicit retry follows OS requestability. Existing channel preparation and coalescing remain intact. Consulted the installed Expo major and matching SDK 57 notification reference before changing the native API boundary.

Add 15 named cases to the already registered runtime test file. Each imports the real coordinator and adapter in an isolated Node process, mocking native/platform boundaries only. Cases cover Android channel preparation and the adapter's Android/iOS permission reads, crossed with Home, opt-out, disposal, failed hydration and a valid active control. They also verify overlapping requests, later implicit retry after cancellation, actual refusal, explicit retry, unchanged saved data and absence of cancellation warnings. iOS fixtures use undetermined authorization followed by nonrequestable denial; Android fixtures retain requestable denial.

The final regression file failed before source changes: 12 cancellation cases failed and four controls/runtime-loading checks passed. The exact same file passes afterward: 16/16. The three original external verification probes also now exit successfully with zero native permission calls after cancellation. Permanent coverage lives in `npm test`, not those external scripts.

All 171 registered Node tests, 15 notification browser scenarios, lint, typecheck and Android/iOS/web exports passed. The web export contains no native access/notification/intent identifiers. Baseline hashes across 373 existing files confirm only the five listed files changed during this fix; unrelated edits and context/feature-plan artifacts were preserved. No dependency, storage schema/key, native configuration or generated native project changed.

The user's warnings/errors-only logging preference takes precedence over generic verbose fix logging. Existing bounded native failure warnings remain; expected cancellation stays quiet. Named tests and assertion diagnostics provide fix feedback without logging saved data or adding debug flags.

No APK was rebuilt or installed for this JavaScript boundary fix. The earlier installed APK therefore does not include it. Physical Android 33+/iOS permission-dialog checks and the feature's extended native acceptance remain pending; exports and mocked native boundaries do not establish those results.

## Prevention

- Revalidate authorization at the final side-effect boundary after asynchronous preparation, rather than only at the caller or after the effect completes.
- Pass a fresh validity predicate across adapter boundaries when the adapter owns additional awaits.
- Distinguish cancelled work from a real refusal/error so cancellation does not change future prompt policy.
- Exercise real adapter code as well as injected coordinator stubs. Hold each meaningful asynchronous boundary and retain positive controls, coalescing and retry assertions.
- Promote temporary verification probes into registered tests, prove the final test fails first, then rerun the same test after the fix.
- Useful additional coverage: physical Android 33+ and iOS permission requests while leaving/returning to the app, including actual denial and Settings recovery. Use a suitable test device; do not infer these results from Android 12 or change the user's device policies silently.
