# Retain touch ownership when the browser takes over wheel panning

**Date:** 2026-11-09 01:19 UTC
**Files:** `src/components/DurationWheel.web.tsx`, `tests/e2e/durationInertia.spec.ts`
**Severity:** medium

## Problem

In the Timer and Planning web duration wheels, dragging from 20 seconds and
holding the same finger stationary for 1.3 seconds enabled Start/Apply before
release. Continuing that touch then left the wheel centered on 23 seconds while
the selected value remained 21. A user could accept a different duration from
the displayed row.

## Root Cause

The web adapter treated `pointercancel` as a physical release. Browsers send
this event when they take over touch panning, even though the finger is still
down. This prematurely moved the shared controller out of `dragging`, allowing
its 1000 ms scroll-end recovery or 160 ms fallback to commit a held gesture.
Subsequent movement belonged to an already-finished interaction.

The shared controller already ignored settling callbacks while dragging; the
missing boundary was the web adapter's ownership of the physical touch.

## Solution

- Track contact through passive `touchstart`, `touchend`, and `touchcancel`
  listeners. Ignore pointer terminal events while an owned touch remains down.
- Use the terminal event's remaining touches and their original targets to
  retain ownership only for this column. Release after its last contact ends
  or is cancelled, preserving browser inertia and existing settling behavior.
- Clear contact ownership on window blur and effect cleanup. Preserve the
  existing pointer-only fallback and remove all added listeners on cleanup.
- Add four real Chrome touch regressions: Timer and Planning, each with native
  `scrollend` detection and the unsupported-event fallback. Hold past both
  recovery deadlines, continue the same touch, and release. Assert action
  gating, unchanged pending state, exact final centering, ancestor offsets,
  and one effective Timer write or an unchanged saved Planning draft.

No new logging was added: the user's warnings/errors-only preference overrides
the generic fix workflow's verbose logging suggestion. This normal input
lifecycle needs no per-frame logs or stored-data output.

## Verification

- Before changing production code, all four new regressions failed at the
  held-touch disabled-action assertion. The exact same four tests passed after
  the fix; assertions and recovery deadlines were retained.
- The original independent real-touch reproduction passed on both screens:
  value 20 remained pending and controls disabled while held; release selected
  23 at offset 1012 (23 × 44), with controls enabled.
- `npm run lint`, `npm run typecheck`, and `npm test` passed (203 Node tests).
- Both duration browser suites passed together: 35 tests, one worker, no
  retries, including real flicks/cancellation, keyboard interruption, no-op
  completion/audio, legacy data, drafts, and six-language/theme layouts.
- `npx --no-install expo export --platform web` and `git diff --check` passed.
- Native adapter, controller, feature plan, manifests, and pre-existing context
  edits were preserved. No APK was built or installed. Physical Android/iOS
  gesture feel and native accessibility acceptance remain pending at the
  user's request to continue without device tests.

## Prevention

- Distinguish browser pan handoff from actual touch release. Increasing a
  watchdog cannot fix an interaction whose finger can remain down indefinitely.
- Reproduce adapter defects with real browser touch input and clocks. Include
  a stationary hold longer than recovery deadlines, continued movement by the
  same contact, final snapping, and persistence/action assertions.
- Check both scroll-end capability paths. Keep contact ownership local to its
  wheel, and clean up test touch input and CDP sessions independently.
- When device testing resumes, repeat prolonged holds, cancellation, multiple
  contacts, and screen-reader adjustments on Android/iOS. Browser tests and
  exports are separate evidence from physical native behavior.
